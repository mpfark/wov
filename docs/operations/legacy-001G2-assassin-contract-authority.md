## Acceptance, target identity and abandonment

[GamePage](../../src/pages/GamePage.tsx)2028–2029 projects active_contract/contracts_completed into dialogue context. [NPCDialogPanel](../../src/features/creatures/components/NPCDialogPanel.tsx)44–50 identifies assassin_contract topic, class and active contract;74–103 implement take/re-roll/abandon, and the rendered controls include Re-roll and Abandon. [Dialogue resolution](../../src/features/creatures/utils/dialogue-topics.ts)128 onward describes the mark and area; presentation's rare-mark Renown text is not a database award.

The only take/abandon definitions found by exact-name search of current SQL are the [June contract migration](../../supabase/migrations/20260629080249_d6091f9a-cb36-4b1f-9beb-4966956f5e93.sql)113–202. They are historical definitions, not a fresh installed catalog read:

- Take calls owns_character before SELECT characters FOR UPDATE. It rejects missing character, class other than assassin, or existing non-NULL contract. It does not accept a client target. Candidates are creatures joined to their node and area, rarity not boss, level max(1,character level−2) through level+1. Selection prefers the region of an arbitrary first Assassin class-hall node, then nearest level, then random. No is_alive predicate or target-row/config lock; target may be dead or later moved/deleted. This is observed selection behavior, not proof the intended policy forbids such targets.
- Stored JSON includes **creature_id UUID**, creature_name, area_id/name, target_level, rarity and issued_at epoch. Display-name equality is not the selection identity. There is no assignment UUID, spawn_seq or acceptance request UUID. No target-node equality, NPC identity, dialogue/config validation, current-node/hall-presence, HP, deleted_at or classless-state check in the function body beyond class comparison. Class-hall region is a selection preference, not proof caller visited the hall. Whether those missing checks violate an approved gameplay requirement needs explicit contract/installed evidence, not a redesigned policy.
- Abandon calls owns_character and directly UPDATEs active_contract=NULL. It has no explicit class, live-contract/version, HP, location or deleted_at check and no request receipt. UPDATE locks the row for its transaction; it does not validate which assignment it clears.
- [Historical owns_character(uuid)](../../supabase/migrations/20260211212345_41f57ff6-5254-4fb2-99cf-eccf43f00fc5.sql)158 uses EXISTS(id and user_id=auth.uid()), returning false for NULL auth.uid(); this inspected definition does **not** reproduce the old NPC-gift nullable-comparison bypass. No admin ownership exception is present there. Installed helper composition remains unverified.

**Re-roll partial outcome is source-established, conditional on these bodies:** UI awaits abandonment success before taking, but sends separate RPC transactions. If A commits then B fails (e.g. no eligible target/class drift/transport uncertainty), A is not rolled back. On B error the UI displays an error and does not call onContractChanged; cached old contract may persist until other refresh. This is a real non-atomic replacement property, not a demonstrated hosted loss or a policy decision that re-roll must be atomic. Standalone take failure preserves the preceding database state inside that transaction.

Concurrency: take holds the character row lock through selection/write, so two ordinary takes for the same character cannot both pass the empty-slot check after serialization. They have no UUID-bound original-result replay: a retry after success receives existing-contract refusal. Abandon and completion updates also lock the row implicitly. An old delayed abandonment can clear a newly issued contract; serial row locks alone do not provide assignment-version binding. Replayed abandon is NULL→NULL absent intervening assignment, but not safely equivalent after a new assignment. No deliberate concurrency test was executed.
