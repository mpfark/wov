## Exact chain and result contracts

[BlacksmithPanel.tsx](../../src/features/inventory/components/BlacksmithPanel.tsx)108–128 and [JewelcrafterPanel.tsx](../../src/features/inventory/components/JewelcrafterPanel.tsx)109–129 check local salvage balance/selling state → functions.invoke('sell-material') with character_id/material_key/amount → [Edge handler](../../supabase/functions/sell-material/index.ts)15–101 auth.getUser → service client reads characters(id,user_id,gold) and materials(key,name,value,tradeable) → consume_material(uuid,text,integer) RPC → characters UPDATE gold with prior-read absolute value → response → onGoldChange/notifyMaterialsChanged/event. Each database request has a separate transaction. No Edge-enclosing database transaction exists; the header comment's atomic/refund claim is not transactional atomicity.

[Latest bounded helper source](../../supabase/migrations/20260511110342_53371110-9a2c-481e-aa15-011d2237f4a2.sql)30–57: positive nonnull delta required, otherwise exception; SELECT count FOR UPDATE on the character/material pair; absent/null/insufficient balance returns boolean false without mutation/error. Sufficient balance decrements count and updates updated_at, returning true. Under ordinary unmodified source and stable locked row, true corresponds to successful UPDATE. It does **not** independently assert ROW_COUNT=1: suppressing triggers, RLS visibility or an unexpected installed definition could alter that implication; zero affected rows must not be presumed impossible from API error absence. No such trigger behavior is demonstrated. Exceptions abort that RPC transaction and normally populate the client error; false is successful transport with a refused domain result. add_material4–28 UPSERT increments and returns new count, not a sale receipt.

The Edge destructures only error from consume, never data. It also treats error-free gold UPDATE as success without a selected row/count assertion. Trigger/RLS suppression or concurrently absent target can therefore yield an error-free no-op; current lifecycle fences may instead raise. The refund is a new add RPC and its return/error is ignored.

## Authority, compatibility and concurrency

Auth user is verified before service use, character ownership compared with user.id; material tradeable/value checked. qty=Math.floor(Number(amount)); finite and positive required. This accepts fractional/coercible inputs by flooring, has no safe-integer/database-integer/product-overflow check, and performs no provider-node/alive/deleted check itself. Normal callers sell salvage only; endpoint accepts any tradeable material and prices salvage at1, others max(0,catalog value). Preserve that pricing and response fields gold_remaining/gold_gained/amount_sold/material_key/material_name; do not invent provider restrictions or economic caps. Rejection of malformed/fractional coercions would be an explicit input-contract tightening, not silent rebalancing; recommend positive JSON integer within actual DB bounds.

[Historical helper ACL](../../supabase/migrations/20260511100551_872301cc-6bea-43ad-9232-1c57a3bf23cd.sql) revokes PUBLIC/anon/authenticated and grants service; later replacement preserves existing function identity privileges, subject to current installed evidence. Helper itself does not check owner/gameplay event. [0006 service grants](../../drizzle/migrations/0006_progression_001f_r1_restore_unprotected_service_updates.sql)167 include gold; browser grants do not. Service capability does not itself validate sale. Effective installed privileges remain unverified here.

Consume serializes one material row only; lock released before gold credit. Two sales can both read goldG, consume serially then write G+a and G+b, losing one credit. Sale may overwrite intervening combat/reward/repair gold changes. Local selling state is UI suppression, not server replay protection; no request UUID in either caller, no ledger in Edge. Lost response/retry can execute a second sale, even where both consume successfully.

## Confirmed and potential failure modes

| Evidence | Consequence |
|---|---|
| **Confirmed source inconsistency:** false consume discarded | Missing/insufficient material result can be followed by gold-credit attempt and success response. Hosted exploit not demonstrated. |
| **Confirmed non-atomic source composition:** consume and credit separate | Failure after successful consume leaves paid-but-uncredited state; best-effort refund is another fallible request. |
| **Potential concurrency conflict:** absolute stale gold write | Lost intervening credit/debit; no multi-session demonstration. |
| **Potential excess refund:** false consume followed by gold error | add can grant materials never consumed because refund runs without knowing consume outcome. |
| **Potential error-free zero-row update** | Response claims credit despite no affected character row; depends on installed constraints/RLS/triggers/concurrency. |
| **Potential duplicate valid sale:** response loss/retry/repeated request | New sale without request binding. No live duplicate established. |
| **Potential numeric/target validity mismatch** | Fractional coercion, large quantity/product overflow or deleted target may fail/refuse inconsistently. Lifecycle guards may already contain deleted mutations; do not claim bypass. |

## Recommended smallest boundary (proposal only)

One service-only SD sale function, conceptually material_sale(actor_user_id,character_id,material_key,integer_amount,request_uuid), called once by sell-material after JWT authentication. Edge supplies verified actor, never trusts an actor from JSON. SQL independently validates actor matches locked character owner and target active, required inputs and tradeable/catalog pricing. Preserve owner-only ordinary sale; no Steward/Overlord override or new role policy. Postgres owner, fixed safe search_path, explicit browser EXECUTE denial/service grant under existing conventions; no broad gold/material grants.

Reuse consume_material **inside the same transaction**, require returned result IS TRUE, then additive characters.gold = gold + gain with RETURNING/one-row assertion. Check amount, count and gold/product against actual installed column bounds; on error roll back ledger, consumption and gold together. No compensating add/refund. Alternatively conditional decrement with RETURNING/one-row assertion only if helper's installed behavior is unsuitable; choose one writer, do not maintain parallel sale implementations. Existing material helper and additive gold pattern are reusable primitives; no suitable existing combined sale function was found in D1/prior named inventory or the targeted sale-name source search. Existing sell_item is inventory/vendor-specific, not a material sale substitute.

Reuse [character_inventory_action_request](../../supabase/migrations/20260908213420_bbfa1b05-0000-4dbf-b662-1ab7e37699c9.sql)13–24 if installed columns/constraints permit: request_id PK, character_id, action='material_sale', inventory_id NULL, arguments={actor,material_key,amount}, result. No new generalized receipt table. Bind actor/target/key/amount; same UUID same payload replays prior success without further grants; conflicting reuse refuses. Validate requester ownership before releasing receipt. Return originally committed response (gold_remaining is an historical result on replay, not a fresh balance); client must refresh authoritative character/material data after success/replay.

Request advisory lock using a fixed sale namespace → character FOR UPDATE → material/catalog row reads (catalog SHARE if required to pin pricing through sale) → consume material row lock → gold update/result. Character-first matches repair/progression/lifecycle resource serialization; no node/encounter/unique lock required. Commit both mutations and ledger together. Inventory-action/repair currently use different request advisory namespaces with shared PK: cross-command UUID collision must refuse/roll back, never overwrite another action's receipt; common new sale namespace alone does not serialize other RPCs. Test that conflict explicitly. No changes to old RPC locking authorized.

Reuse ledger's existing character-lifetime/FK lifecycle; exact installed retention/cleanup must be reconciled before promising protection after deletion/expiry. Keep stable UUID for one logical sale across errors/timeout, fresh UUID for deliberate next sale. A pending retry must not silently adopt another payload; two panels need independent operation state. Preserve UI success/error events and material notifications, add authoritative refresh rather than using replay's old balance as current truth. No approval/audit framework or arbitrary economic limit proposed.

This character→material order is consistent with C resource locking and material helper only locking its own row; standalone add/consume do not acquire character afterward in inspected source. Existing privileged external consumers and catalog/trigger lock composition remain uncertainty. No universal deadlock freedom or hosted concurrency assertion. If installed triggers invert the order, stop before installation and resolve that exact dependency.
