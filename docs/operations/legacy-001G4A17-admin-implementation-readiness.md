Protected `_expected` shape is `{fields:{...},spawn_seq:integer,node_id:uuid|null}`. `fields` is the exact comparison set defined for that operation/dependency closure, not arbitrary client predicates or a global version. For rate use the server's serialized stored-rate key; final persistence name must match reviewed schema (local proof uses regen_bps). Assignment/unassignment need no additional authored fields; deletion uses the listed identity fields. Missing/extra keys, malformed NULLs/types and forbidden fields refuse. Never compare live hp, cursor or encounter state_version as an Admin content revision. A respawn generation change does conflict protected commands.

Recommended consequential success: `{ok:true,kind:committed|replayed,requestId,creatureId,operation,appliedConfig,refreshRequired:true}`; replay also carries the stored original outcome, without rerunning the mutation. Metadata returns `{ok:true,kind:committed|already_matches,creatureId,operation:metadata,metadata,refreshRequired:true}` and has no request/replay assertion. Response classification is not HTTP-status inference. Typed noncommit results carry `ok:false`, explicit kind and `committed:false`; expected-state conflict may return only authorized comparison fields. Transport loss/timeout/unknown server failure remains uncertain. Do not acknowledge committed success until deferred constraints and transaction COMMIT succeed.

Do **not** change existing `public.admin_set_creature_rewards(uuid,jsonb,jsonb,uuid)` parameters `_creature_id,_expected,_desired,_request_id`, JSONB `updated/stale/...` results or reward-specific ledger scope to match these candidates. Use a caller adapter with explicit outcomes, retaining separate requests. A new authoring UUID and reward UUID are separate intents; no cross-ledger UUID-conflict detection is promised.

## Minimal durable receipt/replay design

| Option | Benefits / limitations | Recommendation |
|---|---|---|
| One narrow creature-authoring receipt | One global request UUID within the seven consequential operations; actor/operation/target/immutable args/result bound together. Delete replay needs no live target. One mutex/cleanup contract. | **Recommended candidate**, not an approved schema. Existing reward ledger remains separate; metadata has no receipt. |
| Separate receipt table per operation | Strong isolation but seven near-duplicate stores, cross-operation UUID reuse ambiguity and repeated lifecycle/cleanup code. | Unnecessary for this bounded family. |
| UUID only on creature row / reuse inventory or progression ledgers | Small apparent change, but row deletion loses replay; character-bound/source-specific ledgers have incompatible ownership and semantics. | Reject as insufficient/incompatible; no competing progression/inventory framework. |

Proposed logical storage is `public.creature_admin_request`, owner-private access, with request_id PK, actor UUID, operation, target creature UUID, canonical arguments, server-calculated SHA-256 fingerprint, terminal outcome and timestamps. This is **not DDL**. No cascading FK from target/account can destroy replay; stored UUIDs are references for receipt identity, not permission to inspect players. No full combat snapshot, auth token or generalized notification/audit payload. Narrow target/operation lookup can protect consumed create/delete identity; exact indexes/checks remain candidate review.

Request UUID is generated once by the authenticated Admin caller and retained with immutable payload/expected state until definitive outcome. It is actor-bound, not secret authority. Server constructs canonical JSON from validated typed inputs (operation,contract version,target,expected,payload); never trust a supplied digest. Normalize rates to exact basis points and typed fields before comparison. Full normalized JSONB equality is the match authority; the fingerprint is a server-derived diagnostic/index aid, not permission to accept different arguments or refuse equivalent numeric renderings. Tests must include numeric/format normalization, not just reordered keys. Omitted versus NULL is normalized only by explicit contract. JSONB cannot establish whether original raw JSON contained duplicate keys; do not promise that detection from the SQL function. Same UUID with another actor/operation/target/arguments refuses without revealing its result.

Recommended transaction protocol:

1. Authorize and structurally validate. An authorized side-effect-free committed receipt lookup can resolve replay/conflict **before requiring a live target**, including successful deletion. No mutation or locks on a different stored target during replay.
2. Discover coverage and acquire locks below; take the family request mutex, then reread the receipt. Under a verified supported isolation contract, a concurrent winner becomes visible or causes an explicit retry/serialization failure. Never assume another connection's READ COMMITTED setting proves this RPC's isolation.
3. For a new request, acquire dependent rows, revalidate coverage and expected fields, then execute once. Insert a **terminal nonnull result** atomically with success; no committed pending receipt. Business refusal can be recorded as a terminal noncommit outcome, using an inner rollback boundary if effects had begun. Unknown errors/deferred failures abort the whole transaction and leave no success receipt.
4. Exact retry of a recorded success returns original outcome without redoing rate/maxHP/creation/delete effects. A recorded business refusal also replays its original refusal; changed intent uses a fresh UUID. Infrastructure/coverage abort before durable acceptance leaves no binding/result and requires the caller to retry the original immutable request. Do not claim the database can detect a conflicting reuse of a UUID for a request it never durably recorded.

Deletion replay never re-creates the creature. Creation must refuse reuse of identities consumed by a recorded create/delete, including when no live row remains; it must not interpret missing row as permission to recreate an ambiguously deleted target. Guarantees apply to managed receipt-backed operations, not invented history for previously purged legacy identities. No automatic history repair/backfill.

**Retention/cleanup OWNER DECISION PENDING.** Existing12-month respec/reason-log conventions are operation-specific; they do not automatically approve expiry of these authoring receipts. For local candidate tests only, do not implement cleanup. Before production activation choose duration, late retry behavior, deleted-identity reservation and account/privacy handling. Simply deleting a receipt can allow UUID/identity reuse and destroy exact replay; TTL cleanup is NO-GO without a fail-closed expiry/consumed-identity contract or explicitly bounded guarantee. No cron job or permanent retention policy is authorized here. This does not block writing an isolated local proof under separate authorization.

## Concrete lock and raw-write containment plan

For new commands: authorize/validate/optional receipt fast read → discover source/destination/retained generations and encounter identities → sorted node advisory gates → party-lifecycle advisory gate → sorted existing encounter rows → creature-authoring request mutex → sorted discovered projections/creature/dependent rows → coverage revalidation → expected comparison → settle/mutate/synchronize/terminal receipt → COMMIT. Metadata omits the request mutex/receipt and never settles HP. Creation discovers an absent identity plus destination and refuses changed coverage; missing destination encounters are not created late. No helper discovers/acquires a new node after lifecycle/dependent locks. Unsupported coverage raises retry_required/40001 and rolls back.

Reward integration keeps its existing request-key→reward-creature-key→creature-row order. A separately reviewed early node/lifecycle/encounter phase must precede those two advisory keys, with both keys reserved **before dependent rows**; only then call the existing body reentrantly. Do not use G4A15.cover unchanged, since it already locks dependent rows. Existing/raw callers that use a different order must be reconciled or withheld from that composition; no new inversion is accepted as safe. Current caller isolation and full installed trigger/FK paths remain gates. Do not silently change connection isolation or claim global deadlock freedom.

Proposed **creatures-only browser DML containment**, for later reviewed cutover:

- Route supported browser authoring exclusively through authorized RPCs; preserve creature SELECT/read projections. Close PUBLIC/anon/authenticated direct INSERT/UPDATE/DELETE, including both table and column grants/inherited effective access. Revoking a column privilege alone does not negate a table-level grant. Inspect only directly relevant role/RLS/column access; no database-wide privilege audit.
- Source Admin RLS policies express intent, not proof of effective installed rights. Do not rely on RLS to distinguish an authorized Admin's safe RPC from that same Admin's unsafe raw table update. Review effective browser DML and exact RPC EXECUTE, owner, definer and search_path against fresh metadata before activation; no broad/default privilege change.
- Table DML denial is not function EXECUTE containment. Verify browser access to the already identified legacy creature HP/lifecycle functions from G4 and preserve their reviewed restrictions; a retained SECURITY DEFINER route could still write despite table denial. This is a scoped evidence gate, not a claim that existing historical revocations prove current hosted access or that G4-R2 is fixed.
- Preserve postgres and specifically established trusted service/internal rights for canonical commit, ordinary respawn and Arena; no blanket service-role revocation. New owner-private helpers must deny direct browser execution. Unknown privileged writers remain uncontained until separately dispositioned, not retrospectively approved. A generic service client is not automatically authorized for a new Admin command with no actor.
- Do not install a row trigger that acquires node gates after a creature row lock; do not trust a caller-settable GUC as the authorization escape. Existing semantic validators/generation triggers remain required. Raw-write policy must not block their owner-internal side effects. Fresh parity and native role/trigger tests are required; these documents change no grant or trigger.
