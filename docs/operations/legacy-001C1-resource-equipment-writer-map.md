## Ownership distinctions and formula evidence

- Persistent `characters.str/dex/con/int/wis/cha` are race/creation, class-growth, discretionary investment and trained-stat state. Equipment does not write these columns in the traced canonical path. `resolver.ts:87–110` produces temporary effective fighter attributes by adding usable equipment bonuses; stored base values remain separate.
- `src/shared/formulas/resources.ts:17–70` owns TS formulas: HP class base + twice CON modifier + 5 per level above 1 + flat equipment HP; CP 30 + 3 per level above 1 + 3 times nonnegative INT/WIS modifiers; MP 100 + 10 times nonnegative DEX modifier + 2 per level above 1. SQL sync/progression helpers include bounds HP 1–10000, CP/MP 0–5000; TS helpers themselves do not apply those bounds. Normal-range agreement is not proof for all edge values.
- `src/shared/formulas/items.ts:139–164` resolves per-instance override then template and six gem contributions (garnet STR, topaz DEX, emerald CON, sapphire INT, pearl WIS, amethyst CHA). UI `useInventory.ts:42–47,161–182` and worker resolver use it. SQL resource helpers separately implement only cap-relevant HP/CON/INT/WIS/DEX contributions.
- AC: `src/shared/formulas/combat.ts:226–249` computes class AC + effective DEX modifier + equipment AC + shield 1. Resolver recalculates when a loadout exists; no-equipment path uses persisted maxima/AC (`resolver.ts:92–110`). Attack/damage/block/dodge values are derived from effective attributes/usable equipment and ability state, not stored rewrites of the six base attributes. Combat mechanics are outside this inspection.

## Findings and smallest next step

**CONFIRMED AUTHORITY CONFLICT: none demonstrated.** No gameplay probe or hosted state read. Two concrete source risks deserve priority:

1. **C3 stale resource write (POTENTIAL UNAUTHORIZED WRITER):** sync reads, e.g. HP80 without a row lock; an intervening combat transaction can write HP50; sync then writes the captured/clamped HP80. UPDATE's eventual row lock does not refresh the earlier PL/pgSQL record. The same issue can discard healing or CP/MP changes; no encounter gate/replay corrects it. This is a source-supported interleaving, not proof of installed behavior or a successful revival: other installed triggers remain unknown. Legitimate cap reconciliation needs serialization, not removal of OOC/combat sharing.
2. **Legacy caller-authored amounts (POTENTIAL UNAUTHORIZED WRITER):** C10/C11 bodies prove ownership/party relationship, not a server-authoritative heal/damage event or debit. Client health-transfer debit is a separate write and not required by direct RPC. Existing UI refusal/fences and old grants are distinct from current effective hosted authority. Retain uncertain dependencies; do not revoke or delete on this evidence alone.

Other **EVIDENCE GAP** findings with concrete source differences:

- Equip/unequip then sync is two RPC transactions. Sync error results are not checked before refresh. Repair/wear/strip do not demonstrate automatic max/stat synchronization in the inspected bodies; no cap-sync inventory trigger is established by the reused evidence. Missing inspection is not proof no such installed trigger exists.
- SQL cap helpers use `COALESCE(NULLIF(stat_override,'{}'),template.stats)` while TS effectiveItemStats uses nullish fallback, so `{}` means template stats in SQL but an empty base in TS. A hypothetical gear instance with empty override and template CON2 produces different effective CON/caps. Actual occurrence/intent needs evidence; no historical state rewrite proposed.
- C3/C4 update resource maxima but not AC. Canonical DEX/class changes followed by resource sync can leave the stored AC used by a naked fighter stale, while equipped fighters recalculate AC in resolver. Current commands-paused/race/state means impact is not assumed; full installed AC trigger behavior remains unknown. Do not declare AC universally synchronized.
- Cap/regen SQL and TS formulas agree for traced ordinary arithmetic, with different explicit saturation policies. Retained generic class catalogue versus C2 pinned origin/version rules remain distinct; no new formula policy invented.
