## 2. Exact accounting model

`parseRate` accepts nonnegative finite decimal **strings**, including arbitrarily fine decimal values in the proof; it rejects values above100, exponent notation, whitespace, malformed strings and binary-float inputs. Thus `2.125` is exactly17/8 percent, not a rounded JavaScript Number. This input grammar is a proposed technical API, not a new gameplay restriction. UI normalization/finite production input length and precision need an implementation contract; no silent rounding is acceptable.

Rate r = p/q **percent per minute**, elapsed whole milliseconds dt, maximum M:

`earned HP = M × p × dt / (q × 100 × 60000)`

Use BigInt rational numerator/denominator, normalized by GCD. Add earned HP to the persistent fractional credit; add only floor(total) to actual integer HP and retain the exact fractional remainder. At full HP clamp and discard surplus credit so later damage cannot consume banked healing. Dead creatures never earn credit. Arbitrary rational credit is a reference model; it is not a claim that existing DB columns support it.

The usable interval starts at `max(accounted_through, eligible_since + 60000ms)`. At exactly60seconds the post-delay duration is zero. Settlement advances only the cursor, HP/projection and necessary accounting/version state; repeated identical cutoff is a no-op. No loops over missed ticks, no new timer and no simulated sleep combat. A backwards cutoff is refused, not reinterpreted.

**Partition result:** over the same uninterrupted eligible interval, one settlement and irregular short settlements have identical HP, fractional credit and final accounting boundary, including caps. Version counters differ because transaction counts differ; no claim of whole-state equality across different transaction histories. Tests exercise five rates and four maxHP values, with exact rational comparisons rather than tolerances. No general mathematical verification tool was used; the algebra is additive rational arithmetic and deterministic tests cover the stated cases.

### Required transition instrumentation

Every eligibility-changing writer must supply a coherent cutoff: entry, engagement/damage, relevant effect/action/intent/event creation or resolution, last present-fighter departure/death, reactivation, reassignment, respawn and rate/maxHP edits. Settle the proved previous eligible segment up to that cutoff, then close eligibility on a blocker or start a new 60-second delay when the final blocker releases. Re-observing the same unblocked condition does not restart the delay. Missing transitions cannot be reconstructed from the current snapshot, `last_damaged_at` or wall-clock effect expiry; the proof explicitly assumes this instrumentation and cannot prove its availability.

**Proposed fractional policy, not newly approved gameplay:** preserve already-earned fractional HP across combat interruptions/rate edits, but never count blocked elapsed time. Clear on full HP, death/new generation. This avoids loss of legitimate accrued fractions; owner confirmation is needed before adopting interruption/edit semantics in production. Re-entry still resets the entire60second delay.

## 4. Sleep, initialization and parameter changes

- **Eligible sleep:** settlement after a gap uses the same exact formula as equivalent awake settlements. No continuous simulation or ordinary respawn invocation. Existing authoritative heartbeat or an explicitly supported transaction must eventually settle before a fresh combat snapshot uses HP.
- **Blocked sleep:** unresolved effects/actions keep eligibility closed. No inferred release while the resolver sleeps; a canonical release starts a fresh delay on resume. This is the conservative tested proposal, not newly observed runtime behavior.
- **Initial cutover:** existing wounded rows receive rate5 and an accounting boundary no earlier thanT0. If proved quiet, eligible_since starts atT0; otherwise starts at proved release. No historical heal and no inferred reconciliation of divergent HP copies.
- **Rate edit:** active current-generation attachment is rejected even if empty/quiet. In the inactive test model, settle the old rate to the edit cutoff, preserve exact accrued fractional HP and quiet eligibility history, then use the new rate only for later time. Rate0 accrues nothing and does not disable respawn. Re-enabling does not pay for the disabled interval. Preservation of quiet history/credit during disabling is a proposed policy requiring confirmation.
- **Maximum HP / reassignment:** not rate edits and not implemented in the proof. G4A3's no-refill/clamp proposal and old-parameter cutoff semantics still require a specific decision. Reassignment remains refused/deferred under active attachment; no invented respawn/generation from a rate change. Existing unsafe Admin full-HP saves remain G4-R2.
- **Ordinary respawn:** the proof only receives a supplied ordinary new-generation/fullHP result, resets accounting/credit and retains configured rate. It does not implement due-time selection, death reward eligibility, spawning or a scheduler. A dead zero-rate creature is still eligible for ordinary respawn under unchanged rules.

## 5. Minimal persistence and lock/version contract — proposed, no migration

Existing identity/generation/HP/maxHP/alive fields are reused. Minimal exact reference-state additions on the durable row: rate as exact decimal, nullable eligible-since, accounted-through, fractional-credit numerator and positive denominator. These are **five conceptual values**, with existing spawn_seq scoping initialization/reset. Numerator/denominator stay normalized with0≤credit<1. Native persistence must use checked/exact types; not floating point or JSON Number conversion. A chosen finite fixed rate scale/time precision could encode credit with one fixed-denominator remainder instead, reducing to four values, but that precision has not been approved and is not assumed by this arbitrary-decimal proof. No universal0.01%-precision restriction is introduced.

The proof uses integer milliseconds only. A production PostgreSQL microsecond contract must either preserve exact microseconds with the corresponding denominator or persist a quantized cutoff consistently; dropping fractional time on each call would break partition invariance. Production input/storage bounds and overflow handling need tests before SQL authoring.

Discover nodes and current/retained projections first; acquire sorted node advisory locks, then deterministic encounter locks, then creature/projection dependencies according to the existing commit order. Revalidate coverage/generation and refuse/retry on discovery drift without late node locks. The actual retained SQL/trigger lock composition must be checked before claiming this hierarchy proven. No character-first maintenance loop, unbounded wake-lock loop or new scheduler is proposed.

1. A live claim defers passive maintenance without consuming elapsed credit; the proof models this with an explicit `liveClaim` input. It does not inspect lease/token state itself.
2. HP/projection/accounting/eligibility changes fence old snapshots under the encounter lock and existing version/token controls. The pure model conservatively increments a version even for accounting-only changes; this is a stand-in, not an existing per-creature database version or a mandate to bump every encounter unnecessarily.

**Executed concurrency evidence: NONE.** Tests enumerate serialized orderings and expected-version rejection in immutable objects. ## 6. Comparison and smallest separately authorizable slice

Current source: legacy helpers heal only `creatures.hp` using old guards; wake can full-heal; seed retains an existing same-generation projection; claim snapshots runtimeHP; commit mirrors absolute HP. [G4A](legacy-001G4A-regeneration-hp-ownership.md) demonstrates why this can contradict durable HP and why a row lock or a cosmetic rate UI alone cannot fix it. The proof changes none of these paths.

Recommended next bounded authorization: **local exact blocker/transition coverage and synchronization-candidate design**, incorporating the remaining policy confirmations below. Enumerate the directly necessary writer hooks, deterministic lock/lease/version behavior, seed/ended projection handling and safe configuration edit boundary; then authorize one coherent local candidate, not an isolated new heal writer beside the old ones. No UI-first release and no schema-only activation. A rate-edit-only slice cannot close G4-R1.

The smallest coherent production slice would be one private passive-settlement authority with the selected accounting fields, the necessary entry/seed/claim/commit eligibility and projection-fencing hooks, and replacement of the two independent legacy healing delegates. Include initialization and guarded rate-edit authority; leave CreatureManager integration for a later stage. Its exact hook list must follow the coverage gate rather than assume a wrapper alone can observe every effect/intent/arrival transition. Ordinary respawn and rewards remain existing owners, with only the necessary accounting reset composition.

Prerequisites for that candidate: confirm fractional interruption/edit policy, maxHP policy where required by integration, production exact-decimal/time persistence limits, and complete source-mapped transition coverage. Later installed parity requires a permitted read-only route and separate approval; standard forward Drizzle channel only, historical migrations frozen. No production migration is prepared here.

Rollback risks: reverting to old wake/regeneration after durable accounting starts can reintroduce stale HP/full healing; removing state can lose accrued credit; mismatched UI/server defaults can corrupt rate edits. Future rollout must provide an atomic coherent authority cutover, safe disabled maintenance/recovery mode, retained accounting and explicit old/new dependency checks. Never silently reverse history, resurrect stale claims or repair HP by selecting a preferred copy. No rollback SQL or installation authorization is supplied.
