## A — Source-confirmed idle initiation blocker; incident scope not independently observed

The exact reported tooltip comes from [action-readiness](../../src/features/combat2/action-readiness.ts): presentation idle becomes delivery_unavailable, or an absent model becomes no_authoritative_snapshot. [GamePage](../../src/pages/GamePage.tsx) getCombat2AbilityReadiness previously exempted only requires_active_combat/no_authoritative_snapshot for hostile initiation, excluding delivery_unavailable. Thus a healthy character without an encounter can be blocked from creating the first encounter/snapshot via an enemy-target ability. Automatic [entry hook](../../src/features/combat2/useCombat2EntrySession.ts) also legitimately receives no_engagement on peaceful nodes and records refused/no_engagement while delivery stays idle. This is not a failed server synchronization response.

Class Join uses the existing canonical command and [Recruiter callback](../../src/features/character/components/OrderRecruiterDialog.tsx) → GamePage refetchCharacters → [character delivery](../../src/features/character/hooks/useCharacter.ts). Class is replaced from the fetched row; the newer-resource merge preserves only resource fields, not an old class. Ability lookup reads character.class and level. The [published catalogue](../../supabase/functions/_shared/combat2/active-abilities.json) contains Templar Judgment, enemy target, level1,10CP. No source-only evidence of a missing Templar catalogue entry or progression-control regression was found. The problematic readiness exception already exists at2053fa68 before selective activation; activation exposes previously less-used class abilities, rather than establishing a new SQL failure.

**Local fix:** normalize only the hostile-entry readiness boundary. A healthy idle/no-identity/no-model session with a current creature roster and either idle entry or explicit peaceful no_engagement may submit an intention through the existing [router](../../src/features/combat2/routeCombat2Action.ts) → [entry adapter](../../src/features/combat2/entry.ts) → combat2_hostile_action. No fabricated snapshot, client damage, new RPC, automatic attack or legacy fallback. Active-session actions still require their snapshot. Death, ownership/location transitions, movement, missing roster, uncertain/error/disabled entry, maintenance/authorization refusals and real delivery gap/reconnecting/error stay blocked. Existing level, target, in-flight and spendable-CP checks still run.

This is a **shared Combat2 frontend defect**, reproducible for Judgment/Fireball/Smite, not a Templar-specific or newly-created-character rule. The actual owner session was not recorded: if the reported tooltip occurred during an already active encounter, that may be an independent delivery/snapshot problem and is not declared fixed. Do not clear fighter state or force combat entry to hide it.

**Stances and other abilities:** Holy Shield/Shield Wall use their separate authenticated combat2_character_stances projection/change path; generic idle-entry permission does not bypass that readiness. Their class/level/equipment/CP rules remain. Other non-hostile abilities intentionally requiring combat remain encounter-only per the [approved availability matrix](../design/combat2-ability-availability-and-persistent-stances.md). This fix does not enable every Templar ability at level1 or authorize new OOC effects.
