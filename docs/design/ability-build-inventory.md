## Reading the inventory

All costs below are **activation CP**; there is no authored MP/gold cost. Transfer Health additionally transfers caster HP. Reservation is `floor(current effective max CP × percentage)`, reducing spendable CP without changing raw total. Drop refunds neither activation cost nor resources. Eight stances use character-owned activation/drop and survive ordinary movement/completion/reconnect until explicit drop/death/invalidation. Their triggers execute only through resolver/commit.

Authored “instant” means an active mechanic without a cast queue mode in authoring; under Combat2 it still resolves through the captured action slot/heartbeat. It is **not** permission for browser-immediate effects or OOC use. Enemy actions may initiate through hostile entry. Non-stance self/ally/party/node effects are currently encounter-only. “Modifier” below means the effective attribute modifier/calculation input, not a raw score; authored soft/diminishing/rounding terms remain in the linked JSON and are not rebalanced here. Durations are authored nominal ms/s; [time.ts](../../src/shared/combat2/time.ts) converts them to ticks. Actual wall-clock duration also depends on eligible scheduler opportunities.

Eligibility shared by all actions: ownership/living active character, class/unlock/effective loadout, usable same-encounter target, available CP after reservations and movement/session fences; SQL validates entry/intent and resolver validates the frozen action. Enemy targets must be current living spawns. Ally effects require exact present/living fighter and entry identity plus current/entry party eligibility; Transfer Health excludes self, Divine Aegis explicitly allows self. Ordinary creature-hostile attempts provoke only after valid resolution commits; subsequent DoT/proc/retaliation pulses do not independently provoke new creatures. Source tests do not establish fresh hosted ACLs.

### Common refresh and stacking rules

Resolver replacement matches kind/effect/ability/source/target and creature projection+spawn when applicable. Same-source timed buffs/control normally replace/refresh rather than add an authored stack counter. Absorb refresh preserves the stronger remaining pool; Inspire best_of preserves stronger HP/CP components. Direct DoT recasts increase stacks to their authored cap. Poison/Ignite have explicit source+spawn stack state, cap refresh and source-owned consumption. Cross-source interactions must follow the actual consumer, not an assumption of universal additive stacking. Offense multipliers/crit edges select the strongest compatible bonus; flat/percentage mitigation and outgoing control reductions sum before their caps, while critical chance reduction and same-type amplification use strongest selection. There is no universal additive-stacking rule. See coverage/tests before designing combinations.

### Exact partials and inconsistencies requiring disposition

- **P1 — Divine Challenge:** `mitigation_buff` copies `is_taunt` into effect config/event metadata; the current resolver does not read it to change tank selection. `currentTank()` follows captured tank candidates and the canonical engine uses newest authoritative entry. [Mitigation parameters](../../src/shared/combat2/mitigation.ts) test parsing the flag, not a taunt action. Flat reduction works in source tests. Owner must decide whether “challenge” is mitigation-only wording or a separately specified future taunt. Do not silently override the approved tank rule.
- **P2 — Force Shield magnitude split:** published `amountCalc` is INT + floor(level/ 2), minimum 1; current checked-in [installed stance migration source](../../supabase/migrations/20261001213148_dec8975a-1fb3-43c9-b5a8-73620bd1e0e8.sql) initializes/caps the persistent ward using WIS + floor(level/ 2), with INT driving OOC reformation. Resolver projects `stance.state.ward_remaining` in preference to the mechanic's amount. The SQL authority wins; a timed/INT preview is not live pool authority. Existing [publication contract](ability-publication-and-semantics.md) explicitly preserves the SQL ward formula. Record/align design and presentation before proposing shield variants; do not “fix” balance by inference. Fresh installed function parity remains unknown.
- **P3 — Consecrate scope:** canonical prose says eligible hostile living node creatures, but the aura consumer loops captured creatures and checks only `hp > 0`/`is_alive`, not `engaged`/`is_aggressive`. The [archived claim body](../operations/legacy-001F5-party-parity-envelope.json) captures all encounter `node_creature` rows; the entry source seeds projections and engages only selected/aggressive spawns. Therefore a living passive projection, if captured, is not excluded by that loop. Existing final-closure fixtures contain engaged/aggressive creatures; they do not prove passive exclusion. This is a source scope discrepancy, not proof of a hosted incident; do not silently authorize passive AoE damage/provocation. Resolve scope with the owner before copying this aura into new abilities.
- **Rend:** real current behavior is stackable Bleed; `weapon_based=true` checks weapon contract but adds no weapon strike. Initial weapon damage is already deferred under ENG-ABILITY-001/ENG-BALANCE-001. Status-template Bleed duration20s is not a replacement for Rend's ability-specific DEX duration calculation.
- **Legacy metadata/prose:** `resolved_by=client-loop/client-cast`, `consumes_all_cp`, stance `durationCalc` previews and “guaranteed blocks” remain in some definitions/descriptions. They do not authorize client ticks, all-CP depletion, timed stance expiry or guaranteed blocks in canonical Combat2. Second Wind's amount note says WIS while its actual term is STR. Class descriptions/old manual figures must not override calculation terms or consumers.
- **Live and configuration gaps:** the authoring snapshot is dated; approved local numeric/text differences are not evidence of current Cloud authoring values. Owner-observed Judgment/HP publication does not prove Judgment initiation accepted in live play. Full per-ability, multi-source and independent hosted-session behavior is not established. These are evidence gaps, not declarations that all affected abilities fail.

### Actual loadout structure

[AbilityLoadoutTab](../../src/features/character/components/AbilityLoadoutTab.tsx), [useAbilityLoadout](../../src/hooks/useAbilityLoadout.ts) and [ability-loadout](../../src/features/combat/utils/ability-loadout.ts) group active assignments by role and store `character_ability_loadout` selections. Roles are Signature/Discipline/Doctrine/Pressure/Mastery at levels1/ 5/ 10/ 15/ 20 for defaults; unlock and CP cost remain independent fields. One selection per role replaces that slot in the live class registry. Unknown/unselected options fall back to the class default. UI does not allow changes during combat; the supported `set_ability_loadout` RPC owns writes, not raw browser table mutation. Current client materializes explicit default selections; an older hook header saying “delete default row” is stale, not the current `select()` behavior.

The authored snapshot has **one role with two active options** (Wizard Signature); the other 34 class-role slots have one each. 36 catalogue entries are therefore not36 freely equipable buttons. New alternatives in existing roles are the smallest way to add a real decision without widening the bar or inventing talent points. No ability is proven mathematically mandatory; defaults are implementation choices and universal unlocks, not evidence of balance necessity. Class intrinsic crit/weapon affinity and gear procs are separate systems, not extra passive ability definitions.

## Authoring to playable behavior

1. **Authoring authority:** `base_abilities` owns reusable mechanic/calculation defaults; `abilities` owns configured identity, attributes, statuses and text; `class_ability_assignments` owns class, role, unlock, default and validated overrides; `classes` supplies scaling and `applied_statuses` supplies reusable statuses. [compose-ability](../../src/shared/config/compose-ability.ts) → [effective-ability](../../src/shared/config/effective-ability.ts) is the composition boundary. The checked-in snapshot is release input/evidence, not a second live authoring database.
2. **Publication:** [publish-abilities.ts](../../src/shared/config/publish-abilities.ts), run via [publish script](../../scripts/publish-abilities.mjs), emits versioned identical browser/Edge JSON with source hash, independent CP/unlock fields, role and identity aliases. Invalid override, missing base/role or unsupported record fails publication. Party3s→2s transformation is explicitly retained in metadata, not silently interpreted as a formula change.
3. **Frontend:** [useAbilityRegistry](../../src/hooks/useAbilityRegistry.ts) uses configured joined rows plus the same composition/override functions. [class-abilities](../../src/features/combat/utils/class-abilities.ts) supplies bootstrap presentation fallback; [ability-loadout](../../src/features/combat/utils/ability-loadout.ts) replaces chosen role options. The compiled worker catalogue is not an assertion that fresh browser DB authoring is identical.
4. **Validation:** [GamePage](../../src/pages/GamePage.tsx), [NodeView](../../src/features/world/components/NodeView.tsx), readiness and target resolution route enemy first actions to [combat2_hostile_action source](../../supabase/migrations/20260928100000_combat2_authoritative_arrival_hostile_initiation.sql) then `combat_intent`; ordinary actions use encounter intents. The retained intent core [source](../../supabase/migrations/20260829222108_71c46f91-ec43-43d8-a5bb-dd1b124d6bbd.sql) checks `character_can_use_ability`; later wrappers add spendable-CP, ally, stance and movement guards. Historical SQL establishes source composition, not fresh installed permissions. Stances use the separate authenticated character stance RPC/projection with immutable request identity.
5. **Resolve/commit:** [catalog](../../src/shared/combat2/catalog.ts) class-scoped alias lookup → real mechanic → [resolver](../../src/shared/combat2/resolver.ts) effect consumers, CP/damage/healing/stack proposals → validated atomic SQL commit. Definitions alone do not implement behavior. Intents can be refused at resolution after initial acceptance. Claim cutoff, versions, equipment/stance/fighter identity and spawn generation protect the result. No browser callback owns damage, healing, pulses or rewards.
6. **Release:** publish matching catalogue/mirror; separately review SQL/configuration parity and any actual forward SQL change, deploy both `combat2-dispatch-once` and `combat2-tick-once` when shared worker data/code changes; Mik manually Publishes when frontend code/bundled presentation changes. Git push/catalogue generation alone does none of these. Use the [operating contract](../operations/lovable-supabase-operating-contract.md).

### Adding an ability without duplicate logic

Prefer a new configured assignment/alternative that composes an existing supported mechanic; reuse role/loadout IDs and class-specific authored terms, existing action authority, statuses and effect lifetime rules. Republish both generated catalogues and check actual selected-loadout eligibility rather than only a friendly button. If a behavior is absent, add one shared mechanic/consumer with tests and regenerate the Edge mirror; do not add a class-specific browser damage switch or parallel scheduler. A new stance **identity** currently also needs reviewed SQL changes: `character_stance.ability_key` CHECK and `combat2_change_character_stance` explicitly list eight identities, with SQL cost/reservation/ward rules. Sharing a mechanic is not permission to bypass that closed authority.

Changing a record's target/activation/lifetime is a gameplay contract change even if its mechanic name is unchanged. Per-ability source/configured/SQL/bundle checks and bounded owner gameplay remain release gates; live bundle identity is a recorded limitation, not a reason to repeat the full Combat2 audit.
